`QrBillRenderer` calls `QRBill.Validate` before every render and treats warnings as errors. All three samples pass with no message (otherwise the sample files could not have been written).

`RoundTripTests` decode the generated QR text with the library's decoder and compare with the input record by value. Passed for all three samples.

### (2b) Independent decoder

The QR images were read with a decoder that shares no code with the library (zxing-cpp 3.1.1, Python binding, on the PNG files). For each sample, both `sample-x.qr.png` and the QR code inside `sample-x.png` decode to a QR Code with error correction level **M** (as required by IG chapter 2.5) and the decoded text is byte-for-byte equal to `sample-x.qr.txt`:

| File | Decoded | Equal to `.qr.txt` |
|---|---|---|
| sample-a.qr.png, sample-a.png | QR Code, level M | yes, yes |
| sample-b.qr.png, sample-b.png | QR Code, level M | yes, yes |

## 3. Explanations

### The QR reference and its check digit (modulo 10 recursive)

A QR reference has 27 digits: 26 digits chosen by the issuer (for example a customer number and an invoice number, left-padded with zeros) and a check digit. The check digit is computed with the "modulo 10 recursive" scheme of Annex B of the IG. Walk through the 26 digits from left to right with a carry that starts at 0. For each digit, add it to the carry, take the result modulo 10, and replace the carry by the value at that position in the fixed table `0 9 4 6 8 2 7 1 3 5`. At the end, the check digit is `(10 - carry) mod 10`. Example from the IG: the digits `21000000000313947143000901` give a carry of 3, so the check digit is 7 and the reference is `210000000003139471430009017`. The implementation is `PaymentReference.Modulo10RecursiveCheckDigit`; the same scheme was used by the former orange payment slips (ESR). A QR reference may only be used with a QR-IBAN (an IBAN whose institution identifier is in the range 30000–31999), and only in CHF.

The Creditor Reference (ISO 11649) is the international alternative for plain IBANs: `RF`, two check digits, then up to 21 letters or digits. The check digits are computed with modulo 97-10: write the body followed by `RF00`, replace each letter by its number (A = 10 … Z = 35), take the remainder modulo 97 and subtract it from 98. Validation moves `RF` and the check digits to the end and verifies that the remainder is 1. The implementation is `PaymentReference.Iso11649CheckDigits` and the shared `Modulo97.Remainder`, which the IBAN check uses too.

### The structured address rule

Since 22 November 2025 (IG v2.3), the QR-bill accepts only the structured address type `S`: name, street, building number, postal code, town and country as separate elements. The former "combined" type `K` (two free address lines) is gone. Postal code, town and country are mandatory; street and building number are optional. The lengths are 70 for the name and street, 16 for the building number and postal code, 35 for the town; the country is a two-letter ISO 3166-1 code. Characters must come from the Extended Latin set (IG v2.4, chapter 4.1.1). `StructuredAddress` enforces exactly this; the payload writes the address as seven lines (type, name, street, building number, postal code, town, country), empty where optional.

### Why CHF only

See ADR-0001. In short: the QR-IBAN/QRR variant exists only in CHF, the EUR rules change with v2.4 (and again when EUR bills become SEPA Credit Transfers), and the target users invoice in CHF. Refusing EUR explicitly is simpler and safer than implementing rules that are in motion.

### What changes from v2.3 to v2.4

For CHF bills: nothing technical. The payload keeps version `0200`, the structured address stays mandatory, the character set is unchanged. v2.4 (valid from 14 November 2026; v2.3 remains valid until November 2027) restricts QR-IBAN and QR reference explicitly to CHF, restricts EUR bills to IBAN + Creditor Reference or IBAN + unstructured message (because of the discontinuation of euroSIC and the move to SEPA Credit Transfers), adds Romansh as a correspondence language for the printed headings, and transfers the syntax definition of the "Billing information" line to SIX. The library used here (3.5.1) is declared ready for v2.3 and does not mention v2.4; given the above, that is sufficient for CHF.
