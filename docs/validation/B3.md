# B3 validation record

Unit B3: the React front end in French (`web/`), served by the API, that drives the whole v0.1 flow, and the two additions to the API it needs (`PUT /customers/{id}`, `GET /settings/creditor`). The design and its reasons are in [ADR-0005](../adr/0005-front-end.md). Commands are run from the repository root unless they start with `cd web`.

## 1. Acceptance criteria and where they are checked

| Criterion | Checked by |
|---|---|
| Customers: list, create, edit | `e2e/invoice-flow.spec.ts` (create through the interface, then listed), `CustomerApiTests.A_customer_s_address_is_replaced_with_200_and_existing_invoices_keep_the_old_one`, `CustomerApiTests.An_invalid_new_address_is_refused_with_400_naming_the_field_and_changes_nothing`, `CustomerApiTests.Replacing_the_address_of_an_unknown_customer_is_answered_with_404`, `CustomerForm.test.tsx` |
| List of invoices with state and overdue | `InvoicesPage.test.tsx` (state, *En retard*, total and dates as the API gives them), `e2e/invoice-flow.spec.ts` (the paid invoice in the list) |
| Editor of a draft, issue, PDF download, payment | `e2e/invoice-flow.spec.ts`: a draft with two lines (totals 300.00 then 1'200.00 read from the API's answer), issue with the default dates, download of `facture-<number>.pdf` (a PDF file), payment |
| Settings | `SettingsApiTests.The_creditor_from_the_configuration_is_returned` (QR-IBAN and IBAN), `e2e/invoice-flow.spec.ts` (the IBAN of the configuration on the settings page) |
| Errors of the API shown next to the field or the action | `formErrors.test.ts`, `api.test.ts` (ProblemDetails read into field errors and a message), `CustomerForm.test.tsx` (400 under the field it names, other errors in the alert), `LineForm.test.tsx` (400 and 409 of a line), `IssueForm.test.tsx` (400 under the due date or the payment date, 409 at the issue button), `e2e/invoice-flow.spec.ts` (a refused country code and a refused quantity against the real API) |
| Basic accessibility: labels, keyboard | Every Vitest form test finds the inputs by their label and checks `aria-invalid`, the description of the error and where the focus goes; `CustomerForm.test.tsx` fills and submits the form with the keyboard only; `e2e/invoice-flow.spec.ts` (second test) reaches the pages through the skip link and the navigation and saves a customer with the keyboard only |
| The API serves the front end and its page paths, unknown API paths stay 404 | `InfrastructureTests.The_built_front_end_is_served_at_the_root_and_on_its_page_paths_while_unknown_API_paths_stay_404` |
| OpenAPI document up to date | `InfrastructureTests.The_committed_OpenAPI_document_matches_the_one_the_API_serves` ([`docs/api/openapi.json`](../api/openapi.json), now with `PUT /customers/{id}` and `/settings/creditor`) |
| End-to-end test green in CI | The `Build, format, test and end-to-end` job of `.github/workflows/ci.yml`; the `Front end lint, types, unit tests and build` job runs the checks of `web/` |

## 3. Recording of the flow

Playwright records a video of each end-to-end test (`video: 'on'` in `web/playwright.config.ts`). In CI the videos and the HTML report are uploaded as the `e2e-recording` artifact of the workflow run; they are not committed.
