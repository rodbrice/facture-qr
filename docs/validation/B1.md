# B1 validation record

Unit B1: the invoice model (customers, invoices, lines, states, yearly numbering) and its storage in PostgreSQL with EF Core and migrations. The design and its reasons are in [ADR-0003](../adr/0003-invoice-persistence-and-numbering.md). All commands are run from the repository root.

## 1. Acceptance criteria and where they are checked

| Criterion | Checked by |
|---|---|
| An issued invoice cannot change | `InvoiceTests.An_issued_invoice_cannot_change_and_stays_as_it_was`, `InvoiceTests.Only_an_issued_invoice_can_be_marked_as_paid_and_a_paid_invoice_is_final`, `InvoiceStorageTests.A_stored_issued_invoice_refuses_changes_and_keeps_its_content`, `ConcurrencyTests.A_draft_edited_from_a_stale_copy_after_it_was_issued_is_not_changed` |
| The total is the sum of the lines | `InvoiceTests.The_total_is_the_sum_of_the_lines_after_every_change`, `InvoiceTests.The_total_equals_the_sum_of_the_lines_for_many_random_edits` (500 seeded random additions and removals), `InvoiceStorageTests` (totals read back from the database) |
| Amounts stay within the QR-bill range | `InvoiceTests.The_total_cannot_exceed_the_largest_QR_bill_amount_and_the_refused_line_is_not_added`, `InvoiceTests.A_single_line_cannot_exceed_the_largest_QR_bill_amount`, `InvoiceTests.An_invoice_with_a_total_below_the_smallest_QR_bill_amount_cannot_be_issued`, `MigrationTests.The_database_refuses_an_issued_total_outside_the_QR_bill_amount_range` |
| Numbers are unique under concurrency | `ConcurrencyTests` (40 drafts issued at once on 40 connections, in a year with and without an existing counter; one draft issued from two connections at once), `MigrationTests.The_database_refuses_a_second_invoice_with_the_same_number` |
| Migrations apply to an empty database in CI | CI step *Apply the migrations to an empty database* (`dotnet ef database update` on a `postgres:17-alpine` service), `MigrationTests.The_migrations_apply_to_an_empty_database_and_match_the_model` |

## 3. The concurrency test can fail

A test that passes whatever the code does proves nothing. To check that `ConcurrencyTests` would detect a wrong allocator, the allocation statement was replaced locally by the naive `SELECT COALESCE(MAX(number_sequence), 0) + 1 FROM invoices WHERE number_year = @year`. Both tests that issue 40 drafts at once then failed (several transactions read the same maximum and the unique index rejected the duplicates). The change was reverted; it is not part of the repository.

## 4. Data

Customer names and addresses in the tests are the debtor examples from Annex A of the Implementation Guidelines (Simon Muster, Seldwyla; Pia-Maria Rutschmann-Schnyder, Rorschach). Every database used by the tests is created empty in a disposable container and removed with it.
